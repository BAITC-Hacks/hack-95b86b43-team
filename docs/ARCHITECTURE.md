# Архитектура локального MVP

## Рабочая схема

```text
9 CSV → проверка контракта → InputDataset
                         ↓
                 подготовка продаж
             (клиентские события / stockout)
                         ↓
              сезонность + устойчивый тренд
                         ↓
              календарь запасов и поставок
                         ↓
             рекомендации и объяснения
                         ↓
         правка менеджером → утверждение → CSV
```

Один FastAPI-процесс обслуживает API и собранный интерфейс React/TypeScript. Для разработки интерфейса используется Vite. После сборки браузеру не требуется отдельный Node-сервер. Внешние AI API, ключи и сетевые модели не нужны.

## Границы модулей

| Модуль | Ответственность |
|---|---|
| `backend/app/engine/contracts.py` | Независимый от источника контракт и точные Decimal входных количеств |
| `backend/app/modules/imports/` | Девять канонических CSV, отчёт об ошибках и предупреждениях |
| `backend/app/engine/preprocessing/`, `outliers.py`, `stockouts.py` | Календарь наблюдений, клиентские события, исключения и оценка скрытого спроса |
| `backend/app/engine/forecast.py` | Нормированная сезонность SKU/категории, устойчивый тренд и базовый уровень |
| `backend/app/engine/replenishment.py` | Поступления по датам, lost-sales симуляция, MOQ, кратность, срочность и объяснение |
| `backend/app/modules/calculations/local_service.py` | Снимки входов, исполнение расчётов, заказы и экспорт |
| `backend/app/api/runtime_api.py` | HTTP-запросы, ограничения параметров, маршруты |
| `backend/app/core/store.py` | Локальный SQLite через стандартную библиотеку Python |
| `frontend/` | Обзор рекомендаций, карточка товара, сценарии, данные и заказы |

Ядро принимает типизированные данные и не читает синтетические метаданные. Адаптер реальной выгрузки обязан выдать тот же InputDataset. Отсутствующее поле или другая семантика остатков требует явного преобразования, а не догадки внутри модели.

## Исполнение и хранение

В `data/runtime/workspace.sqlite3` находятся настройки активного набора, расчёты и заказы. Payload хранится JSON в трёх небольших таблицах. Это простой локальный вариант без ORM и отдельного сервера базы данных.

Новый расчёт сохраняет копии девяти CSV в `data/runtime/runs/<run_id>/input/`, параметры и даты контекста. Входам присваивается SHA-256. Подготовленный ряд кешируется в памяти по отпечатку, поэтому новый сценарий не требует повторной обработки неизменных продаж. Результат сохраняется вместе со снимком расчёта. Новый импорт не заменяет прошлые входы и решения.

Один ThreadPoolExecutor с одним исполнителем обрабатывает очередь. API возвращает идентификатор и состояние `queued → running → completed / failed`; браузер опрашивает состояние. После перезапуска незавершённые расчёты помечаются ошибкой: автоматического продолжения или распределённой очереди нет.

Импорт сохраняется в отдельный каталог, проходит полный контракт и только после успеха становится активным. Ошибочный импорт не меняет текущий набор. Источники и выгрузки не публикуются произвольной файловой раздачей.

## Решение менеджера

Заказ создаётся для одного поставщика из готового расчёта. Рекомендованное количество и решение менеджера хранятся отдельно. Изменённое количество требует причины; проверяются MOQ и кратность. Повторное создание для той же пары расчёт/поставщик возвращает существующий заказ.

Состояния — `draft → approved`. Правка и утверждение требуют `expected_version`; устаревшая версия получает 409. Утверждённая версия неизменяема. Для пересмотра требуется новый расчёт и новый черновик. Такой процесс проще полноценного документооборота, но не скрывает изменение утверждённого решения.

Экспорт доступен только для утверждённого заказа. CSV содержит UTF-8 BOM, разделитель `;`, идентификаторы, единицы, согласованное и рекомендованное количество, причину и дату утверждения. Скачивание — действие менеджера; отправки поставщику нет.

## Статистические допущения

- Сезонность строится из нормированных профилей; абсолютные метры и штуки не складываются.
- Тренд рассчитывается по устойчивому направлению недельных наблюдений после снятия сезонности и ограничивается.
- Подтверждённые полные дни stockout не являются наблюдаемыми нулями; оценки не используются как новые фактические доноры.
- Дневная симуляция использует lost-sales: неудовлетворённый спрос до поступления не превращается в задолженность.
- Поставка с просроченным ETA исключается до подтверждения новой даты и сопровождается предупреждением.
- Страховой запас в днях — настраиваемая политика, а не доказанная гарантия уровня сервиса.
- Первое клиентское событие может быть неоднозначным. Последующие данные меняют будущие оценки, не переписывая прошлые решения.

## Границы локального запуска

Приложение предназначено для одного локального демонстрационного процесса на `127.0.0.1`. В нём нет аутентификации и разделения ролей. Блокировки заказов действуют внутри процесса; нельзя запускать несколько worker-процессов с общей SQLite и считать это промышленной многопользовательской конфигурацией.

JSON-payload упрощает разработку, но не заменяет нормализованную схему, миграции и серверный аудит в промышленной системе. Runtime-каталог хранить вместе с SQLite и CSV-снимками при резервном копировании. Разграничение доступа, стратегия хранения и интеграция конкретной конфигурации 1С относятся к внедрению.

Ранее подготовленные пустые каталоги для PostgreSQL, Alembic и отдельного worker сохранены как заготовки. Они не являются зависимостями работающего MVP.
