# Сохраняемый импорт в PostgreSQL

Реализован отдельный рабочий этап, без API и фонового worker. Входы хранятся постоянно,
расчёт может читать выбранную версию из базы вместо Excel. Импорт не создаёт заказ и не
считает неподтверждённые поля достоверными условиями закупки.

## Текущий результат

На локальной машине запущен PostgreSQL 17 в Docker, применены миграции `0001` и `0002`.
Загружены все 12 книг: 261 214 исходных строк, 503 227 нормализованных количественных наблюдений.
В исходные строки входят также сохранённые вспомогательные записи/итоги; приняты для использования
261 034 товарные строки. Для ошибочных/неоднозначных строк наблюдения не публикуются.
Повторная загрузка всех книг вернула прежние ID с `reused=true`.

Создан сценарный набор Systeme Electric `4e124f3e-22c3-4a6f-a798-b737cf075e25`:
история, остатки и путь явно выбраны из TDSheet, кратность — из отдельного MOQ.
Его расчёт дал 408 рассчитанных и 89 требующих проверки строк, полностью совпав с файловым расчётом.
Манифест текущей базы находится в `data/cache/systeme-dataset-manifest.json`, результаты —
`data/cache/systeme-db-preview.json` и `.html`. Эти локальные файлы исключены из Git.

`needs_review` — ожидаемый статус имеющихся исходников, поскольку их бизнес-семантика
не подтверждена. Он не означает сбой загрузки. Список вопросов остаётся в `DATA_AUDIT.md`.

## Запуск на новой машине

1. Создать `.env` в корне по `.env.example`, задать `POSTGRES_PASSWORD` и такой же пароль
   в `DATABASE_URL`. URL должен содержать URL-encoded пароль. Использовать отдельные локальные учётные данные.
2. Из корня выполнить `docker compose up -d postgres`.
3. Из `backend/` выполнить:

```powershell
.venv/Scripts/python -m pip install -r requirements.txt
.venv/Scripts/python -m app.cli db-upgrade
.venv/Scripts/python -m app.cli import-all
.venv/Scripts/python -m app.cli imports
```

Compose публикует базу только на `127.0.0.1:5433`, хранит данные в именованном томе
`elektrokomplekt_postgres_data` и проверяет готовность через `pg_isready`.
`docker compose stop postgres` останавливает базу с сохранением данных; последующий `up -d`
поднимает её снова. CLI читает `.env` из корня независимо от рабочей директории.
Переменные окружения имеют приоритет. Миграции не запускаются скрыто при каждом импорте.

## Команды

Все Python-команды ниже — из `backend/`.

```powershell
# Один файл, поставщик задаётся явно
.venv/Scripts/python -m app.cli import-file "../Systeme electric/MOQ SystemElectric.xlsx" --supplier systeme

# Диагностика с привязкой к листу и строке
.venv/Scripts/python -m app.cli import-issues IMPORT_UUID --limit 100 --offset 0

# Создание зафиксированного набора по собственному JSON-манифесту
.venv/Scripts/python -m app.cli dataset-create ../data/cache/systeme-dataset-manifest.json
.venv/Scripts/python -m app.cli dataset-show DATASET_UUID
.venv/Scripts/python -m app.cli dataset-rows DATASET_UUID --role systeme:sales --limit 10

# Первый расчёт на данных PostgreSQL, без повторного открытия Excel
.venv/Scripts/python -m app.cli preview-systeme --dataset DATASET_UUID --policy ../tests/fixtures/synthetic/systeme_preview_policy.json --output ../data/cache/systeme-db-preview.json
```

`IMPORT_UUID` и `DATASET_UUID` заменить на возвращённые CLI идентификаторы.
UUID в разделе текущего результата действителен только в подготовленной локальной базе.
`dataset-rows` предназначен для явного просмотра данных: не перенаправлять его вывод в общие журналы.
Обычный импорт выводит только идентификатор, имя файла, статус и счётчики.

## Явный выбор источников

Пример манифеста для первой сценарной таблицы:

```json
{
  "name": "Systeme Electric: проверяемый сценарий",
  "mode": "scenario",
  "allow_partial": false,
  "acknowledge_warnings": true,
  "sources": {
    "systeme:sales": {"import_id": "UUID_СВОДНОГО_ФАЙЛА", "kind": "summary"},
    "systeme:inventory": {"import_id": "UUID_СВОДНОГО_ФАЙЛА", "kind": "summary"},
    "systeme:inbound": {"import_id": "UUID_СВОДНОГО_ФАЙЛА", "kind": "summary"},
    "systeme:constraints": {"import_id": "UUID_MOQ", "kind": "constraints"}
  }
}
```

Слева — `поставщик:роль`; возможные роли: `sales`, `inventory`, `inbound`, `constraints`,
`transactions`. Для каждой роли выбирается ровно один импорт и один тип строк.
Продажи двух перекрывающихся источников не складываются. Набор может содержать обоих поставщиков;
первый `preview-systeme` поддерживает общий TDSheet для трёх ролей Systeme и отдельный MOQ.

Предупреждения требуют `acknowledge_warnings=true`. При ошибках импорт можно включить только
с явным `allow_partial=true`; отклонённые строки при этом остаются исключёнными.
Импорты со статусом `failed` и источники без принятых строк активировать нельзя.
Одинаковый манифест возвращает тот же набор. Новый импорт не изменяет предыдущий набор.
Сами манифесты, состав набора и завершённые импорты защищены триггерами PostgreSQL от изменений.

Контекст источника можно передать в `import-file --context source-context.json`:

```json
{
  "scope": "unconfirmed",
  "scope_confirmed": false,
  "semantics_confirmed": false,
  "synthetic": false,
  "snapshot_date": "2026-09-22",
  "inbound_year": 2026
}
```

Дата/год в этом примере — значения, которые вызывающая сторона обязана обосновать;
`import-all` их автоматически не назначает. Без заданного года путь Systeme `24.09` сохраняет
неизвестную дату в нормализованном наблюдении. Даты поставок ИЭК извлекаются из полных дат в заголовках,
при этом «поступление до» сохраняется как крайний срок, а не подтверждённая точная дата прихода.

Неподтверждённый контекст допускается только в `mode=scenario`. `mode=real` требует явных
булевых подтверждений охвата и семантики, но не отменяет последующих проверок расчётного движка.
Синтетические источники требуют сценарного режима; реальные и синтетические источники нельзя смешивать.
Разные контексты одного файла создают разные версии импорта, даже если его байты совпадают.

## Хранение и целостность

| Таблица | Содержание |
|---|---|
| import_batches | SHA-256, имя/сохранённая копия, поставщик, версия адаптера, контекст, время, статус и счётчики |
| source_rows | Импорт, лист, номер строки, тип источника, строковый код, исходные/нормализованные поля JSONB, признак принятия |
| source_observations | Числа NUMERIC, месяц/дата, единица, склад и исходный смысл поля; ссылка на source_rows |
| validation_issues | Уровень, код и безопасное описание проблемы, импорт и строка |
| dataset_versions | Неизменяемый манифест, режим, имя, fingerprint, время |
| dataset_sources | Явно выбранные роли, версии импортов и виды строк |

Это нормализованный слой источников. Он ещё не является окончательным каталогом Product/SupplierProduct
или моделью заказов. Месячные данные развёрнуты в строки; итоги не становятся месяцами.
Значения разных видов источников разделены через kind/semantics и роль в наборе.
Неизвестное хранится как NULL, ноль — как NUMERIC 0, знак сохраняется.
Сохранённые формулы Excel читаются по cached result; их пересчёт не выполняется.

Импорт идентифицируется по хешу файла, поставщику, версиям адаптера/хранилища и контексту,
а не по имени файла. Переименование не создаёт дубль. Advisory lock PostgreSQL сериализует
одновременные загрузки одной идентичности. Пакетная вставка идёт внутри транзакции/savepoint;
ошибка откатывает строки и наблюдения, оставляя статус `failed` с безопасной диагностикой.
Повтор такого импорта использует тот же ID. Аварийное завершение процесса не публикует частичный набор.

Копии файлов хранятся в `UPLOAD_DIR` под SHA-256. Исходники в папках поставщиков не изменяются.
Повторный код внутри товарной таблицы отклоняет все его строки, включая ранее допустимые;
движения по одному товару не считаются дублями только из-за повторения кода.
Защита от одинакового файла не заменяет бизнес-правила дедупликации документов.
Вспомогательные сезонные листы сохраняются отдельно и не удваивают историю продаж.

## Проверка

```powershell
.venv/Scripts/python -m unittest discover -s tests/unit -v
$env:RUN_POSTGRES_TESTS = '1'
.venv/Scripts/python -m unittest discover -s tests/integration -v
.venv/Scripts/python -m pip check
```

Проверены 35 тестов на Python 3.14.7 и PostgreSQL 17. Тесты базы создают схему `test_import_<uuid>`,
применяют/откатывают миграции и удаляют только эту схему. Тесты охватывают точные десятичные значения,
NULL/0/отрицательные значения, сбой после первой вставленной пачки, повтор/конкуренцию,
дубли ключей, частичную активацию, неизменность набора, разделение реальных/синтетических данных
и полное совпадение расчёта из PostgreSQL с расчётом из Excel при запрещённом чтении файлов.
