# Расчёт ИЭК

`preview-iek` подключает месячные продажи, начальные остатки, MOQ и шесть колонок
поставок к общему ядру `robust-monthly-2`. Источники соединяются по строковому коду
1С. Дубликаты и ошибочные строки блокируют позицию; коды без месячных продаж
перечисляются отдельно. Исходные Excel не меняются.

## Запуск

Из `backend/` с установленными зависимостями:

```powershell
.venv/Scripts/python -m app.cli preview-iek --policy ../tests/fixtures/synthetic/iek_preview_policy.json
Start-Process ../data/cache/iek-preview.html
```

JSON и HTML содержат рекомендации, происхождение всех четырёх источников,
поступления с датами, использованный остаток, единицы, диагностику прогноза
и арифметику потребности. Это диагностический сценарий без утверждения заказа.

Для уже созданного набора текущей локальной базы:

```powershell
.venv/Scripts/python -m app.cli preview-iek --dataset 83e97509-729d-41cd-905b-2d2924f5d55f --policy ../tests/fixtures/synthetic/iek_preview_policy.json --output ../data/cache/iek-db-preview.json
```

База должна быть запущена. На другой машине импортировать источники и создать
сценарный набор через `dataset-create`: нужны роли `iek:sales` (`sales_monthly`),
`iek:inventory` (`inventory_monthly`), `iek:inbound` (`inbound`),
`iek:constraints` (`constraints`). ID импорта выбирать явно.
Локальный манифест сохранён в `data/cache/iek-dataset-manifest.json`.
Режим БД не открывает Excel. Отклонённые строки загружаются только для диагностики
и блокировки соответствующего кода, их значения не участвуют в расчёте.

## Остаток и поставки

Поставляемая политика явно использует `historical_opening_proxy`: начальный
общий остаток 01.09.2026 подставляется как условный свободный остаток в сценарий
22.09.2026. Это не актуальный снимок и не восстановление движений/резерва.
Данные об отсутствии товара из такого снимка не выводятся.

Другие варианты `stock_mode`:

- `unknown`: запас неизвестен, рекомендация блокируется.
- `explicit_snapshot`: используется только запись `snapshots[код]` с полями
  `date`, `storage_unit`, `available_stock`. Дата обязана совпасть с датой расчёта,
  единица — с единицей хранения источника. Отсутствующая запись остаётся неизвестной.

Пример отдельного актуального снимка в политике (значения условные):

```json
{"stock_mode": "explicit_snapshot", "snapshots": {
  "EXAMPLE_": {"date": "2026-09-22", "storage_unit": "м", "available_stock": "120"}
}}
```

Дата каждой поставки читается из части заголовка «поступление до ДД.ММ.ГГГГ»,
а не из даты документа. Разные поставки в один день сохраняются отдельно.
Поступления на границе/после горизонта исключаются; поздняя поставка не снимает
ранний дефицит. Подтверждённость задаётся явным boolean `assume_inbound_confirmed`.
Пустые ячейки и отсутствующая строка означают ноль только при явных политиках
`blank_inbound_quantity: zero` и `missing_inbound_row: zero`. Включённый пример
использует эти сценарные допущения; без них неизвестный путь блокирует расчёт.
Количество в пути предполагается выраженным в единицах хранения.

## Единицы, MOQ и кратность

MOQ из «мин. разр. к отгр.» означает минимум, а не кратность. Поле `minimum_unit`
явно выбирает `storage` или `order`. В первом случае минимум делится на коэффициент
`storage_units_per_order_unit`, затем применяется отдельная `order_multiple`.
При нулевой потребности минимальная партия не создаёт заказ.

`unit_rules` задаёт общие сценарные правила (в примере только штучные товары).
`products` переопределяет правило целиком для конкретного кода. Для метров нужен
именно индивидуальный коэффициент; длина бухты из названия не извлекается.
Без пересчёта или отдельной кратности положительный заказ блокируется.

Пример правила для вымышленного товара:

```json
{"products": {"EXAMPLE_": {
  "storage_unit": "м", "order_unit": "бухта",
  "storage_units_per_order_unit": "100", "order_multiple": "2"
}}}
```

При минимуме 500 м это минимум пять бухт, округляемый до шести при кратности две.
Политика в репозитории не содержит выдуманных коэффициентов для реальных бухт.
Охват склада, резерв, единицы MOQ/пути и сроки нового заказа остаются вопросами
для согласования с партнёром. Категории и коэффициенты источников не интерпретируются.

## Проверка

На текущих исходниках: 2463 позиции, 457 рассчитаны (52 с положительным заказом),
2006 требуют уточнений. Большинство блокировок вызвано неполной или отрицательной
историей. Это результат выбранных допущений, не список закупок к отправке.

Проверены совпадение Excel/PostgreSQL, неизменность исходных файлов, происхождение
остатков, даты поставок, неизвестные значения, дубликаты, перевод метр/бухта,
различие MOQ/кратности и совпадение объяснений с количеством. Общий набор:
50 unit-тестов, 17 интеграционных и пять числовых приёмочных тестов.
Следующий этап — пользовательский сценарий: API, сохраняемые задания,
интерфейс, правки, утверждение и экспорт заказов.
