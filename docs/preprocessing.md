# Подготовка продаж — этап 3

Это исторический объяснимый слой подготовки, не прогноз и не расчёт заказа. Он принимает существующий InputDataset и возвращает PreparedSales. Исходные CSV, модели импорта, synthetic generator и API не изменяются.

## Зачем нужна подготовка

Продажа показывает отгрузку, а не всегда обычный спрос. Возврат уменьшает фактический net; отсутствие товара скрывает спрос; проектная партия может завысить среднее. При этом регулярный крупный клиент — часть нормального бизнеса. Удалять все большие покупки нельзя.

Порядок внутри каждого дня: нормализация и агрегация → проверка наличия → оценка клиентских событий по прошлому → исключение подтверждённых аномальных строк из baseline → восстановление stockout по прошлым чистым наблюдениям. Обнаружение разовых заказов предшествует использованию наблюдения для stockout: иначе выброс попал бы в среднее восстановления.

## Запуск

Из корня проекта в установленном окружении:

```powershell
.\.venv\Scripts\python.exe -m backend.preprocess_sales --input data/synthetic --output data/preprocessed
```

Даты по умолчанию соответствуют синтетике этапа 2: history-start=2024-09-01, history-end=2026-08-31, as-of-date=2026-09-01. Для других данных все три даты нужно передать явно. Текущие часы и metadata.json не используются.

Для исторического среза добавьте `--cutoff-date 2026-04-22`. Вход проверяется существующим валидатором за весь заявленный период, затем preprocessing игнорирует продажи после cutoff. Окно склейки: `--split-window-days 5` (допустимо 3–7). Параметры Python API находятся в PreparationConfig.

Результаты записываются отдельно от источника:

- daily_demand.csv — полный дневной ряд, включая доступные дни без продаж.
- normalized_sales.jsonl — все строки до cutoff, исходная Sale, signed_qty, признаки и причины.
- customer_events.jsonl — оценки клиентских событий **на каждую дату поступления новых строк**. event_id повторяется для продолжающегося события, предыдущие оценки неизменны.
- summary.json — версия, параметры, диагностика и TOP 10 крупных событий.

JSONL сохраняет Decimal строками без потери точности. В daily CSV списки причин и ID записаны как JSON в ячейке, пустые числовые поля означают None. Вся папка data/preprocessed исключена из Git. CLI возвращает ненулевой код при ошибке импорта/подготовки. API-эндпоинт для тяжёлого расчёта на этом этапе не добавлен.

## Типы и нормализация

Дата уже имеет тип date, qty/unit_price — Decimal после загрузчика этапа 1. Сохраняются sale_line_id, customer_anon_id, warehouse_id, sku, order_id, operation_type и источник.

sale даёт положительный signed_qty, return — отрицательный. Нулевые qty разрешены контрактом, но не создают положительного клиентского события.

Технический дубликат — тот же sale_line_id и полностью совпадающие бизнес-поля, кроме source_file/source_row. Повтор остаётся в normalized_sales с is_technical_duplicate=true, но не участвует в суммах. Разные ID с одинаковыми значениями не удаляются. Один ID с разными данными вызывает ошибку. CSV-валидатор по-прежнему блокирует любой повторный ID: дедупликация ядра предназначена для прямых типизированных вызовов и не ослабляет импорт.

Дневная группировка: date × sku × warehouse_id. gross_sales_qty — сумма sale, return_qty — положительная сумма return, net_sales_qty = gross - return. transaction_count — число недублирующихся строк, не число уникальных order_id. unique_customers включает клиентов продаж и возвратов. max_single_customer_qty — максимальная сумма положительных продаж одному клиенту за день.

## Календарь и stockout

Текущие пары берутся из inventory; начало ряда — максимум history_start, products.active_from и inventory.availability_start. Историческая пара без текущего inventory начинается с первой известной продажи до cutoff. До появления товара нули не достраиваются.

Полные stockout-дни берутся только из [start_date, end_date_exclusive), с обрезкой по периоду. Нулевые продажи и текущий нулевой остаток сами по себе не доказывают историческое отсутствие. Вне stockout считается availability=1: это допущение требует полной истории наличия от источника.

Доноры восстановления — только реальные доступные дни **строго раньше T**, без исключённых событий. Нулевые доступные дни включены. Оценённые stockout-дни никогда не возвращаются в историю как наблюдения. Отрицательный net сохранён в выходе, но его вклад в неотрицательную донорскую интенсивность ограничен нулём.

Восстановление:

1. Последние 28 подходящих наблюдений в пределах 90 календарных дней.
2. Если среди них минимум четыре дня того же дня недели — среднее этих дней (`weekday_28d`). Оно ограничено сверху тремя средними по всему окну.
3. Иначе при хотя бы семи наблюдениях — среднее окна (`recent_28d`).
4. При недостатке собственных наблюдений — медиана средних других SKU той же категории, базовой единицы и склада (`category_fallback`). Донорский SKU должен иметь минимум семь доступных дней. Если собственные данные всё же есть, категорийная оценка ограничена тремя собственными средними.
5. Если подходящих соседей нет, но есть несколько собственных дней — их среднее с insufficient_history=true.
6. Если данных нет — 0, `zero_history`, недостаток истории явно отмечен. Этот ноль означает отсутствие надёжной оценки, а не доказанное отсутствие спроса.

При изменении окна названия weekday_Nd/recent_Nd меняются вместе с N. Выводятся число наблюдений, число соседних SKU и последняя дата донора. Если донор старше 28 дней, оценка отмечается недостаточно надёжной; после 90 дней он недопустим. Каждый день длинного stockout проверяется заново: нельзя бесконтрольно умножать прежний средний спрос на длительность отсутствия.

Категорийная оценка грубая: одинаковые единицы не гарантируют одинаковую популярность SKU. Это явный резервный метод с низкой надёжностью. Для редкого спроса четыре совпадающих дня недели могут дать ноль — вероятностный прогноз на этом этапе не строится.

## Крупные клиентские события

Сначала положительные строки группируются по customer × sku × warehouse × date. Несколько разных order_id в один день одного клиента рассматриваются вместе. Известный order_id связывает строки между днями, но только внутри окна 3–7 дней от начала события. Без order_id объединяются близкие покупки того же клиента с тем же товаром и складом. Окно закреплено на первой дате, не растягивается цепочкой на весь месяц. Разные явные order_id в разные дни без общей связи не склеиваются автоматически.

Для оценки используются исключительно прошлые чистые дневные наблюдения. Типичный дневной уровень — максимум медианы и среднего с отсечением 10% значений с каждого края. MAD — медиана абсолютных отклонений от медианы.

Порог подозрительно крупного события — максимум:

- типичный уровень × max(8, 3 × число календарных дней события);
- (медиана + 8 × 1,4826 × MAD) × число дней события;
- 6 × медиана положительных дневных значений;
- 4 × эмпирический 95-й перцентиль дневных значений окна.

Так используются одновременно масштаб SKU и обычный разброс. Нет фиксированного порога «больше 500». При MAD=0 score использует положительную типичную величину; при полностью нулевой истории автоматического исключения нет.

`is_large_customer_event` — подозрение, не решение об исключении. Для исключения дополнительно требуется:

- минимум 28 чистых наблюдений и шесть положительных дней;
- количество выше четырёх максимальных дневных объёмов за предыдущие 90 дней;
- отсутствие сопоставимого регулярного события этого клиента.

Регулярность подтверждает прошлое отдельное событие за 5–62 дня (нижняя граница равна окну склейки), с количеством от половины до двойного текущего, ранее не исключённое. Также сохраняются прошлые количество событий, среднее, медиана и максимум клиента. Один случайный высокий score не отменяет повторяемость.

Достаточная регулярность → `retained_recurring_large_customer`. Мало истории → `large_event_insufficient_history_review`. Есть подозрение, но не пройден строгий порог исключения → `large_event_uncertain_review`. Только подтверждённое правило даёт is_outlier=true, is_excluded_from_baseline=true и `excluded_large_customer_event`.

Эти правила являются объяснимой эвристикой, а не доказательством разового назначения заказа. По первой крупной покупке нового клиента принципиально невозможно знать, повторится ли она. Начало ряда обрабатывается консервативно; статистические ложные срабатывания всё ещё возможны. Пороги не читаются из synthetic metadata.

## Без использования будущего

Обработка идёт по календарным дням. Для всех SKU в день T сначала выполняются оценки по истории до T, и лишь затем добавляются фактические наблюдения дня. Это исключает зависимость от порядка SKU и попадание сегодняшних соседей в категорийный fallback.

Если раздробленный заказ пересёк порог на третьем дне, первые два дня **не переписываются**. Исключаются новые строки с момента обнаружения. Предыдущие версии оценки события остаются как были. Возврат ранее исключённого заказа сопоставляется по точному customer × SKU × warehouse × order_id; предыдущие дни не пересчитываются.

Backtesting должен подавать справочники и доступность в том виде, в каком они были известны на дату расчёта. В CSV нет `known_at`/версий задним числом исправленных данных: ядро обеспечивает отсутствие использования будущих дат, но не может восстановить историю правок внешнего источника.

## Итоговый baseline и возвраты

В доступный день:

`demand_for_baseline = net_sales_qty - excluded_sales_qty + excluded_return_qty`.

Удаляется только количество отмеченных строк; обычные продажи других клиентов остаются. Возврат исключённого заказа сохраняется в фактическом net, но не уменьшает регулярный baseline второй раз. Если order_id отсутствует или связь неизвестна, возврат уменьшает net обычным образом.

Отрицательный net и отрицательный baseline сохраняются с `negative_net_returns_preserved`, чтобы не скрывать возвраты. estimated_demand ограничен нулём снизу. Следующий этап должен явно определить работу с отрицательным net, а не трактовать его как отрицательную вероятность спроса.

В stockout-день baseline равен неотрицательной оценке потенциального спроса за вычетом обычных возвратов. Она не добавляется к net повторно. observed_sales всегда показывает фактический signed net.

Положительная продажа одновременно с полным stockout — противоречие. Импорт этапа 1 его блокирует. При прямом вызове ядра день получает STOCKOUT_SALES_CONFLICT, estimated_demand=None, demand_for_baseline=None и причину ручной проверки. Даже при крупном заказе оценка не добавляется поверх продажи. Такой день не является донором.

## Диагностика и ограничения

generate_preprocessing_report возвращает количество исходных/обработанных/будущих строк, дублей, дневных записей, SKU и складов, stockout-дней, оценок (в том числе положительных), крупных и исключённых событий, возвратов, SKU с недостатком истории, SKU с нулевым baseline, конфликты и TOP 10.

Крупные/исключённые события считаются по уникальному event_id, а не по числу строк или оценок продолжения. insufficient_history_sku_count включает начальный период обучения, поэтому может равняться всем SKU; отдельное поле insufficient_history_sku_at_cutoff показывает состояние на конец обработки. Нулевая оценка stockout учитывается как оценка, положительные подсчитаны отдельно.

Сводка input_rows описывает весь загруженный файл, ignored_future_rows — отрезанную часть. Дневные результаты и флаги до T неизменны при добавлении будущих продаж; общая диагностика количества входных строк естественно меняется.

Финальный прогноз, годовая сезонность, тренд, safety stock, urgency, рекомендации поставщикам, UI и утверждение не реализованы. Добавленных зависимостей нет.
