# Проверка работающего MVP

Полные критерии и ручной сценарий находятся в [ACCEPTANCE.md](ACCEPTANCE.md), сценарий выступления — в [DEMO.md](DEMO.md). Этот файл описывает реальные тесты; пустые заготовки в backend/tests не означают пройденную приёмку.

## Запуск

Из корня проекта:

```powershell
.\.venv-win\Scripts\python.exe -m pytest -q
.\.venv-win\Scripts\python.exe -m pip check
```

Допустимо другое установленное стандартное CPython-окружение. `tests/conftest.py` создаёт отдельный временный каталог внутри проекта для каждого запуска, чтобы избежать старых Windows TEMP с чужими правами. Кеш pytest отключён.

Frontend собирается из своего каталога командой `npm run build` после установки зависимостей. TypeScript-проверка и сборка не заменяют ручную проверку действий в браузере.

## Что покрывается

| Файлы | Проверки |
|---|---|
| tests/test_health.py | Health, главная страница и диагностические маршруты |
| tests/test_run.py | Безопасный запуск и занятый порт без остановки чужого процесса |
| tests/test_ingestion.py, test_validation.py, test_cli.py | Контракт CSV, строки, BOM, дроби, leading zeros, связи, интервалы, CLI и коды возврата |
| tests/test_synthetic.py | Воспроизводимость, сценарии, баланс запасов, отделение истинного спроса |
| tests/test_preprocessing.py | Возвраты, клиентские события, регулярность, stockout, причинность и отсутствие мутации |
| tests/test_preprocessing_synthetic.py | Реальные проходы по контролируемой синтетике и граница metadata |
| tests/test_preprocessing_cli.py | Выходные файлы подготовки и ошибки CLI |
| Остальные tests/test_*.py текущей сборки | Расчётное ядро, API, заказы и экспорт; точный перечень доступен через pytest --collect-only |

Число тестов не закреплено вручную в документации: актуальный результат — последняя строка полного запуска pytest. При ошибках сборка не считается готовой только потому, что часть тестов прошла.

## Обязательные регрессии

- Восстановление stockout использует более ранние доступные наблюдения, никогда будущие продажи.
- Восстановленная оценка не становится фактическим донором для следующего отсутствия.
- Исключённый разовый заказ сохраняется в аудите и не входит в регулярный baseline.
- Крупный клиент может быть признан регулярным при следующей сопоставимой покупке даже после первоначального исключения.
- Сезонность, рост, запас и даты поставок влияют на количество на контролируемых рядах.
- Ранняя потеря спроса не скрывается поздним поступлением.
- MOQ не создаёт заказ из нулевой потребности.
- Неверная версия блокирует изменение заказа; утверждённый заказ не редактируется.
- Неутверждённый заказ нельзя экспортировать как утверждённый.
- Новый импорт не изменяет сохранённый результат предыдущего расчёта.

## Пределы оценки

Пройдённые тесты подтверждают свойства алгоритма на заданных входах. Они не доказывают экономию партнёра или универсальную точность. Генератор намеренно создаёт проверочные условия снабжения и не является моделью реальной закупочной политики.

Для оценки на реальных данных нужен backtest на нескольких датах отсечения с обучением только на прошлом и сравнением с простым средним и сезонным базовым прогнозом. Нельзя оценивать скрытый спрос во время реального stockout как известный факт. Для редких продаж MAE и агрегированный WAPE при ненулевом знаменателе полезнее MAPE.
